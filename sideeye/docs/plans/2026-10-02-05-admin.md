# Plan 05 — Admin Panel Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Role-gated admin: dashboard, products, orders, coupons (+assign-to-user), reviews, users.

**Architecture:** `/admin/*` server components behind `requireAdmin()` + middleware (Plan 02); mutations as server actions with zod schemas; image upload goes through a single storage interface that writes to `public/uploads` on local disk in v1.

**Tech Stack:** Same as Plan 01.

**Spec:** design spec §2, §8, §9.

**Scope note:** this plan serves two audiences. Tasks 1–2 are the internal admin panel. Task 3 is the customer-facing account area (`/account/*`), which ships in the same plan because it is the same owner-scoping guardrail work.

## Global Constraints

- JavaScript only. Every admin read AND mutation checks `role === "ADMIN"` server-side.
- Order transitions validated against the state machine; cancel/refund restores stock + coupon in the same transaction (reuse Plan 04 logic).
- Coupon create/edit validates value ranges (percent 1–100, sane max-discount).
- Never expose full PII beyond what the order screen needs; never log it.
- Money is never aggregated across a user's orders anywhere in `/account` (owner decision). One order's own total is shown on that order's receipt; no lifetime-spend, no cross-order sum, no dashboard total.

## Decisions

- **Hosting:** VPS first, so product images live on local disk in `public/uploads` as originally planned. Cloudflare R2 arrives only once the store passes roughly 1000 active users. `lib/storage.js` is the single seam, so the swap is one file; when R2 lands, add its host to `images.remotePatterns` in `next.config.js`, and if the app ever runs more than one instance, `lib/rate-limit.js` needs a Redis equivalent behind the same two-function API.
- **No migration for addresses.** The `Address` model has existed since Plan 01 with no UI attached, so Task 3 is UI only. The one new column in this plan is `User.dateOfBirth DateTime?` — nullable, no backfill, applied as manual SQL plus `migrate resolve --applied` because `migrate dev` is blocked by drift in this repo.
- **`/account` is a profile card plus two link blocks**, not a stats dashboard (owner decision). No order counts, no order rows, no money on it. `/account/orders` is the record; `/account` is the profile and the way in.
- **The checkout "deliver to" picker is out of this plan.** It ships with RELEASE-CHECKLIST §5.4/§5.5 as one address block.

## Review Focus

- Non-admin POST directly to an admin action is rejected (no client-only gating).
- Setting stock negative or price non-integer-paise is rejected.
- Illegal order jump (e.g. delivered → pending) is rejected with a clear error.
- Deactivating a user (`isActive=false`) immediately blocks their next request.
- Deleting/deactivating a product with open orders never corrupts historical OrderItems (snapshots preserved).
- User A cannot read User B's order detail or address by guessing the id in the URL — the page 404s rather than rendering someone else's data.
- The order detail page renders from `addressSnapshot` and the `OrderItem` snapshots, so a later edit to a saved address never rewrites order history.
- `/account` never aggregates money across orders.
- Deleting a saved address never touches any order.

### Task 2: Orders + coupons + reviews + users

**Files:**
- Create: `sideeye/lib/order-status.js` — the transition map, which does not exist yet
- Create: `sideeye/app/admin/orders/page.jsx`, `sideeye/app/admin/coupons/page.jsx`, `sideeye/app/admin/reviews/page.jsx`, `sideeye/app/admin/users/page.jsx`, `sideeye/actions/admin-ops.js`

**Interfaces:**
- Consumes: Plan 04 order machine/coupon rules; `requireAdmin`.
- Produces: order list + guarded status buttons; coupon CRUD + assign-to-user (UserCoupon); review approve/reject; user list + `isActive` toggle.

**`lib/order-status.js`** — built first, because today `Order.status` is a bare string whose seven legal values live only in a comment, and nothing enforces a move. This module owns the map (`pending → confirmed → packed → shipped → delivered`, cancel only from `pending`/`confirmed`, refund after delivery) and exports `canTransition(from, to)` plus the legal targets for a given status. Every status write in the app goes through it, admin included. An illegal jump such as delivered → pending is rejected with an error naming the legal moves.

**Reviews are a live gap, not a nice-to-have.** `POST /api/reviews` already stores every review with `isApproved: false` and only approved ones render on the product page. Until this screen exists, a shopper's review is invisible forever. Build it in this task.

- [ ] **Step 1: Build `lib/order-status.js`** with unit tests for every legal and illegal transition.
- [ ] **Step 2: Build the four screens + actions.** Status change validated by that map with the timeline appended in the same transaction; coupon value ranges checked (percent 1–100, sane max discount); every action re-checks `role === "ADMIN"` server-side.
- [ ] **Step 3: Verify** — coupon assigned to user X works for X, rejected for Y; review approval makes it visible on the product page; cancelling an order restores stock; `delivered → pending` is refused.
- [ ] **Step 4: Commit** — `git commit -m "feat: add admin orders, coupons, reviews and users"`

### Task 3: Customer account area (profile, addresses, orders)

**Files:**
- Modify: `sideeye/app/account/page.jsx` — placeholder becomes the profile card + two blocks
- Modify: `sideeye/app/account/orders/page.jsx` — each row links to the detail page
- Create: `sideeye/app/account/orders/[number]/page.jsx`, `sideeye/app/account/addresses/page.jsx`
- Create: `sideeye/actions/profile.js`, `sideeye/actions/addresses.js`
- Migration: `User.dateOfBirth DateTime?`

**Interfaces:**
- Consumes: `requireUser` (`lib/guards.js:58`), `cancelOrder({ orderId })` from `actions/checkout.js:295`, `formatPaise`, the existing `Address` model, `Order.timeline` and `Order.addressSnapshot`.
- Produces: `updateProfile(input)`, `createAddress(input)`, `updateAddress(input)`, `deleteAddress(input)`, `setDefaultAddress(input)`.

**`app/account/page.jsx` — the whole page, fully specified.** A profile card showing photo, name, DOB, email, phone. An Edit toggle on the card reveals a form for name, DOB and phone; email stays read-only because it is the Google identity. Two blocks below it link to Addresses and Orders. Nothing else — no stat tiles, no order rows, no thumbnails, no money anywhere on this page.

Photo displays from `User.avatar`, which Google returns at sign-in, so there is no upload UI in v1. `next.config.js` currently has no `images.remotePatterns`, so an avatar served from a Google CDN host would fail to render through `next/image`: add the pattern for whichever host a real session's `picture` value actually uses (confirm it from a live session, do not guess), or fall back to a plain `<img>` at fixed dimensions.

**`app/account/orders/[number]/page.jsx`** — that one order's items, subtotal / discount / shipping / total, delivery address rendered from `addressSnapshot`, payment method and status, and the status timeline read from the existing `timeline` JSON. The timeline renders defensively: the column is untyped JSON, so a malformed value falls back to the status pill alone rather than crashing. A Cancel button appears when status is `pending` or `confirmed`, reusing `cancelOrder`.

**`app/account/addresses/` + `actions/addresses.js`** — list with a default badge, add / edit / delete, and set-default performed as a single transaction that clears the other defaults for that user. UI only; the model already exists.

**`actions/profile.js`** — zod: name 1–80 chars, DOB optional and never in the future, phone optional and 10 digits. DOB is PII: never logged, never required to order, and not surfaced in admin beyond a label.

**Guardrails.** Every read scoped `where: { userId: user.id }`. Every action re-reads the session through `getCurrentUser()` so the `isActive` check runs, so a guessed order or address id fails. Deleting an address never touches an order.

**Explicitly not in this task:** the checkout "deliver to" picker. It ships with §5.4/§5.5.
